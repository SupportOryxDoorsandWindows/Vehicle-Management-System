# Editing & Expense Assignment — Phase 2 (Sub-project 2) Design

**Date:** 2026-10-12
**Owner:** Business Support (Oryx Doors & Windows)
**Status:** Approved for implementation (next sub-project chosen by owner)

## Summary

Lets Admins maintain the fleet register in the app instead of the source
spreadsheets: add and edit vehicles, add and edit expenses, and assign the
Unassigned Expenses to the right vehicle. Every change of an expense's
vehicle is recorded in `expense_assignment_audit` by the database itself.
Viewers see none of these controls, and RLS (from Sub-project 1) already
rejects their writes.

## Why This Is Next

Sub-project 1 added the Admin/Viewer write rules but nothing in the app
writes yet. Twenty-three imported expenses sit in Unassigned Expenses with
no way to fix them, so they are missing from every per-vehicle cost figure.

## Scope

### Vehicles
- **Add vehicle** (`/vehicles/new`) and **Edit vehicle**
  (`/vehicles/:id/edit`), Admin-only routes.
- Editable fields, grouped on the form: identity (plate, make, model, type,
  fuel, seats, chassis, gear, tyre size, registration date, condition,
  status), assignment (driver, department, owner), documents (vehicle
  licence expiry, CID permit start/expiry, advertisement permit
  start/expiry, renewal status, branded), service (last service mileage,
  warranty, free service, remarks), finance (instalment start/end, months,
  years, monthly repayment, flat rate, finance amount, EMI status).
- Not editable here: `upload_*` (Uploads sub-project), `source_id`
  (import provenance), `created_at`.
- Plate numbers are normalised with the import script's `normalizePlate`
  (trim, collapse spaces, uppercase) so new plates match the same way
  imported ones do. A duplicate plate gets a clear "already exists" error.
- No delete: set status to Inactive. This keeps expense history intact.

### Expenses
- **Add expense** from a vehicle's Expenses tab (vehicle preselected) and
  from Unassigned Expenses (no vehicle) → `/expenses/new`.
- **Edit expense** (`/expenses/:id/edit`) from both lists.
- Editable fields: vehicle, date, expense, type of expense, description,
  supplier, cost, category, job status, payment terms, quotation number,
  invoice number, employees, teams, requested by, approved/rejected by,
  approval date, paid by, payment date, grouped reference.
- Not editable here: file fields (Uploads sub-project) and
  `raw_vehicle_number_text` (what the spreadsheet originally said — kept
  as evidence for why an expense was unassigned).
- Category is required. On a new expense it is suggested from type and
  expense name using the import script's `deriveSystemCategory`, until the
  Admin picks one themselves.
- Cost, if given, must be a number ≥ 0.
- No delete in this sub-project.

### Assignment
- Unassigned Expenses gets a per-row vehicle picker + **Assign** button
  (Admin-only). Changing the vehicle on the Edit Expense form is the same
  operation.

## Data Model Changes (migration `0004`)

- `vehicles.id` and `expenses.id` get `default gen_random_uuid()` so the
  app can insert rows (Phase 1 ids were generated by the import script).
- `expense_assignment_audit`:
  - add `previous_vehicle_id uuid null references vehicles(id)`;
  - make `assigned_vehicle_id` nullable so moving an expense back to
    "unassigned" is recorded too;
  - `assigned_by` stores the acting user's id (`auth.uid()`), as text to
    match the existing column.
- A trigger on `expenses` writes one audit row whenever `vehicle_id`
  changes on UPDATE. Insert with a vehicle is not an "assignment" and is
  not audited (the row's own `created_at` covers it).
- The trigger function is `security definer`, and the "Admins write audit"
  policy is dropped. Audit rows can then only be written by the trigger:
  an Admin cannot forge, edit, or delete history through the API. Everyone
  logged in can still read it.

## UI Gating

Same rule as Sub-project 1: Viewers do not see Add/Edit/Assign controls at
all, and the new routes are wrapped in `RequireAdmin`. RLS remains the real
boundary.

## Errors

Saves show the database's error inline and keep the form filled in. RLS can
turn a forbidden update into "0 rows changed" rather than an error, so every
update reads its row back and treats "no row" as a failure (same pattern as
Manage Users).

Concurrent edits are last-write-wins. This is acceptable for a small team of
Admins and is noted for the Audit History sub-project.

## Testing Approach

- Unit/component: form field mapping (blank → null, numbers parsed, plate
  normalised), validation messages, category suggestion, Viewer sees no
  edit controls, save failure keeps the form and shows the error.
- Database (`supabase/tests/editing_and_assignment.sql`, run on a plain
  local Postgres with `supabase/tests/supabase_stub.sql` standing in for
  Supabase's roles and `auth.uid()`): Admin can insert/update vehicles and
  expenses; duplicate plates are rejected; each change of `vehicle_id`
  writes exactly one audit row with previous and new vehicle and the
  actor, and unrelated edits write none; Admin cannot insert, edit, or
  delete audit rows or call the trigger function; Viewer and anonymous
  writes are rejected.

## Explicitly Out of Scope

Deleting vehicles or expenses, file/photo uploads, bulk import from the app,
audit history UI, export, reminder configuration, maintenance/mileage
history entry.
